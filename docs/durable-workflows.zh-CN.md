# 多 Agent 协作与 Durable Workflow 的边界

Harness³ 的协作层把共同目标、Agent 身份、能力、贡献与评审组织成可管理的执行过程。执行层需要持久工作流语义：进程中断后保留已完成贡献，未完成任务继续协调，未知外部效果显式等待处置。

[Temporal 的 Durable AI 文档](https://docs.temporal.io/ai) 将 Agent 应用、处理流水线和内部 Agent 平台列为典型场景。Harness³ 与其中的内部 Agent 平台重合：多个 Agent 共享队列和执行基础，由平台管理并行、依赖、等待、取消、恢复和返工。

| 执行概念 | 当前 Harness³ 对应 | 当前边界 |
|---|---|---|
| Workflow | Goal、ResearchJob、任务依赖、评审轮次 | SQLite 状态协调；没有确定性事件重放 |
| Activity | 模型请求、工具调用等外部步骤 | 单 Run 内执行；尚未把所有外部步骤独立持久调度 |
| Worker / Task Queue | 本地持久 Run 队列和 4 个并发槽 | 单 daemon；没有跨机器租约与所有权 fencing |
| 扇出 / 汇合 | 并行研究、依赖完成后的汇总 | 显式 DAG 与有界调研模板；没有任意动态图 |
| 人工交互 | 待验收、返工意见、未知消息结果处置 | 部分本地交互；尚无通用审批等待协议 |
| 执行历史 | Run、检查点、事件、轮次、产物 | 可追溯记录；不等价于 Temporal 的完整事件历史 |

控制面接受命令时，以事务提交状态、幂等回执与事件；协调器只从持久状态派发，模型不能自行改变所有权或无限创建实例。模型调用和外部工具执行无法与 SQLite 事务原子提交，须单独处理超时、中断和未知结果。平台不能将“调用者没收到答复”解释为“外部动作未发生”。重放工作流和自动重试 Activity 也不能独自保证外部效果恰好一次；工具需要幂等键、结果查询或对账协议。

Agent 协作还需要工作流之外的对象：Preset、独立实例与会话、插件能力锁、消息作用域、版本化贡献、评审、派生谱系和预算归属。这些规则应保持在协作领域层，不依赖某个具体调度后端。

当前保留 Rust + SQLite 的本地启动路径，不引入 Temporal 服务依赖。后续按真实多机需求评估执行后端接口：本地后端或 Temporal 后端都必须遵循相同的身份、幂等、取消、贡献版本和未知结果契约。是否采用 Temporal、采用哪套 SDK 以及控制面/Worker 兼容边界仍待专门设计；本文不声明已完成该集成。
