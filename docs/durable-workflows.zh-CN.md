# 多 Agent 协作与持久工作流

Harness³ 将共同目标、Agent 身份、能力、贡献与评审组织成可管理的执行过程。持久工作流为这些过程提供执行基础：保存已完成工作，协调依赖和等待，处理取消、重启与结果未知。两者的关系是领域模型与执行机制的组合。

[Temporal 的 Durable AI 文档](https://docs.temporal.io/ai) 将 Agent 应用、处理流水线和内部 Agent 平台列为典型场景。Harness³ 的组织与调度需求与内部 Agent 平台重合，但 Agent 身份、母体、能力绑定和证据验收仍由平台领域定义。

| 工作流概念 | Harness³ 领域对应 | 需要明确的契约 |
| --- | --- | --- |
| Workflow | Goal、ResearchJob、任务依赖与评审轮次 | 状态转移、取消、恢复、输入与版本 |
| Activity | 模型请求、工具调用等外部步骤 | 调用身份、回执、幂等、超时与未知效果 |
| Worker / Task Queue | Run 队列、执行容量与所有者 | 认领、并发、租约和失联后的提交权限 |
| 扇出 / 汇合 | 并行研究、委派、依赖完成后的整合 | 任务拓扑、贡献版本和终止条件 |
| 人工交互 | 验收、返工意见、结果未知处置 | 持久等待、唤醒输入与处理权限 |
| 执行历史 | Run、检查点、事件、轮次与产物 | 可追溯记录、可重建输入与保留策略 |

接受命令时，应以事务提交状态、幂等回执与事件；协调器从持久状态派发工作。模型请求和外部工具无法与平台数据库原子提交，因此必须区分确定失败、成功回执和结果未知。“调用者没有收到答复”不能证明外部动作未发生。事件重放或 Activity 重试也不能单独保证外部效果恰好一次，工具还需幂等键、结果查询或对账协议。

Agent 协作需要额外表达 Preset、独立实例与会话、插件能力锁、消息可见性、版本化贡献、Review 和派生谱系。这些规则属于组织服务，不依赖具体工作流后端。调度后端只能在获准状态转换内推进执行，不能替代权限、证据或验收规则。

本地后端通过 SQLite 状态协调运行，不具备确定性事件重放或跨机器 Worker 所有权语义，也没有 Temporal 服务依赖。若适配 Temporal 等执行后端，必须保留相同的对象身份、命令幂等、取消、贡献版本及结果未知契约，并单独验证 SDK、控制面和 Worker 的兼容边界。后端选择不改变这些领域约束。

实际可用能力与限制见[当前平台状态](status.zh-CN.md)，完整分层见[架构设计](managed-agents.zh-CN.md)。
